# Changelog

All notable changes to this project are listed here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- A streamed reply stays smooth in a long chat. Stored messages no longer render again on every new word, and the words that arrive within one screen frame are drawn together. On a phone class CPU with 200 messages on screen, a fast reply went from about 11 to about 49 frames per second.
- Mascots that are off screen stop following the pointer and stop blinking, so a long chat does no work for them.
- The mascot's eyes move much further toward the pointer and the caret, and the whole cloud leans a little the same way, so the look reads on a small mascot too. Under reduced motion the eyes and the lean still move, without the glide.
- New messages, the streamed reply and panels move in with short transform and opacity animations, and the bot list slides over more softly on a phone. Buttons give a little when pressed. Reduced motion turns these off.
- The server lets the browser keep the built web app files, whose names change with each build, for a year. The page itself is checked on every visit, so a new version still shows at once. A repeat visit no longer downloads the app again.

### Fixed

- The plus in the new bot and attach buttons sits exactly in the center of the round button.
- `share_file` works on Windows and macOS. The file must stay inside the workspace, and the opened file must be the one the path leads to, checked by file identity. Linux uses the same check. On Windows the open does not refuse links, so the realpath and identity check are the guard there.
- The buttons inside the Rules panel had no background and their text could not be read.
- The header buttons are one group now. On windows up to 1200px wide they sit in a row after the bot name instead of covering it, and on a phone they take a second row.
- `browser_click` checks the focus after a click. A click on a field that did not take the focus is repeated once, and the result tells the model whether a field has the focus.

### Added

- The browser tab shows the cloud mascot. It shows the thinking face while the open bot works, and a red dot when its reply arrives while the tab is in the background, until you look at the tab again. Safari shows the plain icon only, since it does not use SVG tab icons.
- New bots: the "+" button makes a bot, and its chat asks for its name and job. A bot can also make one with `bot_create`, after the owner approves the name, title and first instructions. The new bot uses the same Claude sign-in as the others. A bot is deleted from its chat after a confirm. Its chats, rules, routines, watches, webhooks, secrets, connected apps, integrations, uploads, shared files and workspace go with it. A running turn stops first, and the last bot cannot be deleted.
- Local mode: a warning prints at start, and the setup chat says once that the bot runs as the owner, with their files and account. The install docs say so too.
- Local mode keeps CloudBot's Claude login in its own folder under the data dir, so it no longer replaces your own Claude Code login. Owners who upgrade must sign in to Claude again once. The setup chat has a Sign out action for CloudBot's login only.
- Without a browser of its own, the bot does not open a page on the host computer. It can still read pages with WebFetch and WebSearch.
- Local browser: without Docker, the bot starts its own Chrome, Chromium or Edge. It is found in the usual install paths, or set with `CLOUDBOT_BROWSER_PATH`. The browser has its own profile folder in the data folder, and DevTools listens on loopback only. Its traffic goes through the same gate that blocks private addresses. `request_screen` hands the window to the owner, and the Screen panel shows the page live and passes on the owner's mouse and keys. Without a browser, the browser tools stay off, and the bot says it cannot browse. With `CLOUDBOT_AGENT_USER` set, the local browser stays off, since it would run as the server user. The browser tools stay off until the gate is checked to refuse a private address. A browser left open by a crash is reused when it is the bot's own.
- API integrations: the bot writes a script in its workspace and registers it with `integration_create`, with the sha256 of the file. The owner approves a card that shows the whole script, the hash, and the secret with the site it belongs to. A script is at most 8000 bytes, and a change whose card cannot be shown is denied. The script gets one secret from the vault as an environment variable, and no other variable from the server. The secret is removed from the output on a best effort basis. The approval card is the real control. A changed script does not run until the owner approves the new version with `integration_update`. Each run goes through the review like a shell command. Runs go one at a time, as their own user, `cloudbot-integrations`, which cannot read the vault. Before and after each run the user's processes, files and IPC objects are wiped, and each run has process and file size limits. Integrations stay off unless `CLOUDBOT_AGENT_USER` and `CLOUDBOT_INTEGRATION_USER` are both set.
- Code on GitHub: the bot's `git` and `gh` work on repositories and pull requests. The owner saves a token as the bot secret `GITHUB_TOKEN` in the secure form, for https://github.com. The token never reaches the bot's shell, and a token for another site is never sent. Reads such as clones, fetches and GET requests go through with no card. A push, a write to the API or a GraphQL mutation waits for the owner in the chat, and the card names the repository, the pull request title or the review or comment. A denied request gets a 403 that says so, and a write with no token saved gets a 401 without asking the owner. The Docker image adds `git` and the official GitHub CLI.
- Connect apps: the bot adds a remote MCP server by its https or http address, when the owner asks in the chat. A private address works only when the owner allowed its host for the browser. A token goes through the secure form to the vault, is sent only to its own https site, and never reaches the model, the messages or the logs. The bot reaches the server through a local proxy that adds the token. The owner must approve each new server. The tools of a connected server go through the same review as the bot's other tools. The bot lists and removes servers too, and the "Connect apps" panel lists them with their status and tool count and removes one.
- The browser cannot reach private or local addresses. Chromium sends its traffic through a SOCKS5 gate in the server. The gate connects only to public addresses, checked at the address it connects to. The owner can allow one private host with `browser_allow_host`, which always asks for approval. Loopback, localhost, this machine, link-local and the cloud metadata addresses can never be allowed. The bot's shell is not covered by the gate.

- Webhook hardening: a call with an `X-Delivery-Id` header is queued once per 24 hours, and a repeat answers `200` with `duplicate`. Each bot can have 10 webhook messages waiting, and a call past that gets a `429` that says so. The last 20 refused calls of each webhook, with a fixed reason and time, are shown to the owner in the Routines panel and to the bot in `webhook_list`. The refused calls and the delivery ids are kept in memory only.
- Bot mascot: each bot has a cloud mascot next to its name, in the sidebar, the chat header and beside its last message in a run of replies. The face follows the bot: calm when idle, looking at the caret while the owner types, excited while it works, sparkles when a turn is done, a wink when it waits for the owner, sleepy during a usage limit wait, and X eyes after an error. The eyes follow the pointer on every mascot. While the owner types, the eyes turn along the text box with the caret, from left to right, and look down at it. The mascots blink at random, every 2.5 to 6 seconds. Under reduced motion the eyes and the blink still work, but the eyes jump to the new spot instead of gliding. The bounce, the squish and the hover motion stop. A new bot gets a random color and shape from ten colors and four shapes, and the bot can change them with `profile_set_mascot`. Existing bots start blue with the puff shape. The `avatarColor` field is removed from `GET /api/bots` in favor of `mascotColor` and `mascotShape`.
- Stalled turns: a turn that sends nothing for 10 minutes is stopped, and the chat says so. Time the owner is asked, such as an approval or a screen handoff, does not count. A turn that already stopped for another reason gets no second message.
- Command floor: a short fixed list of commands the bot always refuses, checked before the review agent. It covers wiping the root, the home, data, workspace or upload folders, formatting or writing to a disk, a fork bomb, stopping or editing the cloudbot service or container, and reading or copying the vault files or the data folder, in Bash and in the file tools. Wrappers such as `sudo` are skipped, and the text of `bash -c`, `eval` and similar is checked again. No rule, approval or model choice can lift it, and a command that cannot be checked is refused. The refusal gives a short reason and never repeats the command.
- Turn limits: the owner sets a time limit in minutes, a spending limit in USD and a step limit per bot, once for chat turns and once for turns started by routines, webhooks and watches. Each limit is optional. A limit stops the turn like Stop does, and the chat message names the limit and its value. The time limit counts working time only, and it pauses while the turn waits on the owner. The agent and the review agent are each held to the spending limit, so a turn can spend up to twice the limit. The spending is an estimate, and a subscription is not billed by it. The bot sets limits with `limits_set`, and the Models panel has a Limits section. The owner uses `GET` and `PUT /api/bots/:id/limits`.
- Page watches: the bot watches a web page for the owner with `watch_create`, and is woken only when the visible text changes, with a short diff. Default check every 60 minutes, minimum 15. An optional keyword limits the watch to lines that contain a word. The bot lists and deletes watches with `watch_list` and `watch_delete`, and the owner lists and removes them in the Routines panel. Only http and https pages are read, and private, local and reserved addresses are refused, also after redirects. Pages are read with a 15 second limit, 1 MB and up to 3 redirects. Watch turns use the routines model and effort.
- The bot can make a webhook from the chat with `webhook_create`, for example "make a webhook for my form tool". The URL is shown once in the open web app, with the same keep-secret note and Hide button as the Routines panel. The bot never sees the URL, and the URL is not stored. Each URL the bot makes gets its own notice. If no web app is open for the bot, no webhook is made, and the bot asks the owner to open the web app and try again.
- Effort per kind of work: the Models panel sets how much thinking chat, routines, the review agent, the browsing helper and the documents helper get, with one effort select next to each model select. "Default" keeps the CLI default. The bot can set it in the chat with `models_set`, for example "use haiku for the browser" or "think hard on chat". `GET /api/bots/:id/models` also returns the allowed effort levels, and `PUT` refuses an unknown level without saving anything.
- Webhooks: the owner creates a URL in the Routines panel. When an outside service sends a `POST` to it, the bot gets a chat message named after the webhook, with the body marked as data. The call waits in the same queue as chat messages and uses the routines model choice. Only a hash of the token is stored, so the URL is shown once. Calls are limited to 30 a minute per bot, and bodies to 64 KB. The bot can list and delete webhooks. The owner uses `GET`, `POST` and `DELETE /api/bots/:id/webhooks`.
- Models panel: the Models button in the conversation header sets the model of each kind of work, with a select per kind. Helpers show "No helper" when unset. `GET /api/bots/:id/models` also returns the allowed aliases. The bot can change its models in the chat with `models_set`, which goes through the review agent.
- Helper agents: the owner can pick a model for `browsing` (the browser tools) and for `documents` (the file tools and `share_file`). A helper exists only when its model is set. The main agent hands that work to the helper with the Agent tool. The owner's blocked tools apply inside helpers too. The helper choices use the same `GET` and `PUT /api/bots/:id/models`.
- Model choice per kind of work: the owner picks a model for chat turns, for routine turns and for the review agent, with `GET` and `PUT /api/bots/:id/models`. An unset choice keeps the CLI default. A choice is an SDK alias (`fable`, `opus`, `sonnet` or `haiku`) or a full `claude-` model id. Routine turns use the routines choice and fall back to the chat choice.
- Routines panel: the Routines button in the conversation header lists the bot's routines with their prompt, their schedule in UTC, the next run and the last run. Remove deletes a routine from the list. The panel says the bot creates routines when asked in the chat and marks routines that are off.
- Routines from the chat: the bot has `routine_create`, `routine_list`, `routine_delete` and `routine_set_enabled`, up to 20 routines per bot, with schedules in UTC. The owner can read and remove routines with `GET /api/bots/:id/routines` and `DELETE /api/bots/:id/routines/:routineId`. Creating, deleting and changing a routine go through the review agent. Listing does not.
- Routine scheduler: every 30 seconds the server checks for due routines and sends each prompt to its bot as a chat message, so the queue, usage waits and approvals apply. A routine missed while the server was off runs once. There is no way to create a routine from the chat yet.
- Routine storage: a `routines` table keeps a prompt, a schedule (every N minutes with a 5 minute minimum, daily, or weekly, in UTC) and the next run time for a bot. Nothing runs them yet.
- Review agent: before a tool call runs, a separate model call with no tools reads the call, the owner rules and the last chat lines. It answers allow, ask or deny. Reading and looking tools skip the review. Sending a message, a purchase and a booking always ask the owner. A review that fails asks the owner too.
- Approval gate: a tool call can wait for the owner. The chat shows a question with Approve and Deny. Deny, Stop, a restart and one hour without an answer all refuse the call.
- Document tools: the image has Python 3 with openpyxl, python-docx, python-pptx, reportlab, pypdf and matplotlib, plus pdftotext from poppler-utils. The bot builds spreadsheets, documents, slides, PDFs and charts in its workspace and sends them with `share_file`. The system prompt names the tools. The container check imports every library as the bot user.
- Screen handoff in the web app: the Screen panel shows who holds the screen. The owner can take it and give it back with Done, take over, or keep it. The panel accepts mouse and keyboard only while the owner holds the screen, and it follows a handoff the bot starts.
- Screen handoff on the server: the bot has a `request_screen` tool that gives the screen to the owner with a note in the chat. While the owner holds the screen, the `browser_` tools and `browser_type_secret` refuse to act. The owner takes or returns the screen with `POST /api/desktop/screen/take` and `POST /api/desktop/screen/release`, and reads the holder with `GET /api/desktop/screen`. The live view drops mouse, keyboard and clipboard input unless the owner holds the screen.
- Live screen: a Screen button in the conversation header shows the bot's desktop in the chat with noVNC. The view is view only. The server proxies a WebSocket at `/api/desktop/vnc` to x11vnc on `127.0.0.1:5900` and refuses requests without the session cookie.
- Rules panel: a Rules button in the conversation header opens the owner rules of the bot. The owner can add allow and block rules, name blocked tools and remove rules there.
- Owner rules: each bot has allow and block rules in plain words, stored on the server and read for every turn. The sentences go into the system prompt, and block rules can name tools that the SDK then refuses. Routes: `GET`, `POST /api/bots/:id/rules` and `DELETE /api/bots/:id/rules/:ruleId`.
- `browser_type_secret`: the server types a saved secret into the focused password, one-time code or card field, only on the site saved with it. The bot never sees the value.
- Screenshots in the chat: `browser_screenshot` takes `showOwner`, and the screenshot then also appears in the chat. The chat shows a preview of PNG, JPEG, GIF and WEBP files up to 5 MB above the download link.
- Browser tools: the bot can open web pages, read them, take screenshots, click, type, press keys and scroll in the Chromium on its desktop. Only http and https addresses can be opened, and page content is framed as data for the model.
- Secrets the bot asks for: with the `request_secret` tool the bot asks the owner for a password, a code or a payment detail. The chat shows a secure form with the https site where the value will be used. The value goes to the vault, tied to the bot and the site, and never reaches the model or the chat history.
- Desktop: the image has a virtual screen with Chromium, a terminal and a VNC server, run as the bot user. The server starts it and starts it again when it exits. Chromium and VNC listen on localhost only. Default choices that wait for the owner are in `docs/OWNER_QUESTIONS.md`.
- File downloads: the bot can send a file from its workspace to the chat with the `share_file` tool. The server copies the file (at most 50 MB, regular files inside the workspace only) and the chat shows a download link. Downloads need the session cookie and are sent as attachments.
- Shared file cleanup: copies of files the bot shared are removed `CLOUDBOT_UPLOAD_RETENTION_DAYS` days after they were shared, in the same daily job as the upload cleanup. A copy is also removed when its message cannot be saved.
- Image check: before an attached image goes to Claude as an image block, its header and end marker are checked and its sides must be at most 8000 pixels. A file that fails is still listed by path.
- Upload cleanup: files are removed `CLOUDBOT_UPLOAD_RETENTION_DAYS` days after the upload (default 30). Files that were never sent are removed after one day. A bot with a running or queued message keeps its files. The cleanup runs on start and once a day.
- Messages sent while a bot answers are queued and run in order after the current turn. When Claude reports a usage limit, the turn waits for the reset time, then continues. The chat shows when it resumes. Queued messages and waits survive a restart, and Stop cancels the wait and the queue.
- Scripted Claude setup in the first bot's chat, with subscription sign-in or
  an API key form, persisted progress, retry messages and guarded answer routes.
  Answered forms close in the web app. API mode starts the local key proxy and
  keeps the real key out of the agent environment.
- Optional agent execution as the bot user with restricted sudo, a minimal environment and workspaces outside the server data folder.
- Persistent bot home and workspace volumes for Claude credentials, sessions and bot memory. The CLI in the home volume updates itself across image upgrades.
- Attachments: `POST /api/bots/:id/attachments` saves uploaded files in a per-bot upload folder that the bot can read but not change, up to `CLOUDBOT_MAX_UPLOAD_MB` (default 20). The next message lists the files, and PNG, JPEG, GIF and WEBP images up to 5 MB also go to Claude as images. The web app shows the files in the user message.
- Claude subscription login helpers for the setup chat, with sign-in links,
  code submission, cancellation, timeout handling and CLI status checks.
- Project setup: server with a health route, lint, tests, CI and docs.
- Secrets vault with encryption at rest, a secure form endpoint and a local key proxy that adds the API key to requests.
- SQLite storage for bots, messages and settings with Drizzle ORM, with migrations that run on start. Migrations are found next to the install, not in the working directory.
- Agent runner that streams one conversation turn through the Claude Agent SDK.
- Bot profile: the bot can change its own name, title and description from the chat, and its system prompt says who it is and where its memory lives (`CLAUDE.md`).
- One-command install on Debian and Ubuntu (`docker/install.sh`) with a free sslip.io HTTPS name or your own domain, and the `cloudbot` command for status, logs, update and setup links. See `docs/INSTALL.md`.
- Docker image and compose file with Caddy in front for HTTPS. The server runs as `cloudbot` and the Claude Code CLI is installed for `bot`. The data volume is readable only by `cloudbot`. CI builds the image and checks the health route and the isolation of the data folder.
- Chat API: list bots, read and send messages, stop a running turn, and stream the turn events over Server-Sent Events.
- Live replies: the chat shows the text of an answer as it is written. The default bot CloudBot is created on the first start.
- Older messages: the chat loads the page before the oldest message when you scroll to the top. `GET /api/bots/:id/messages` takes `before` and `limit` (default 50, capped at 200).
- Chat web interface in `src/web`: bot list, Markdown messages, setup messages and a composer. The server serves the build from `dist/web`.
- One-time setup link printed on start. Opening it sets a session cookie, and every `/api` route except health needs that cookie. A new code ends the old sessions.
- `pnpm setup-link` prints a new setup link for an owner who lost the cookie. Set `CLOUDBOT_PUBLIC_URL` to make the link use your public address.

### Fixed

- Claude login and auth status use the isolated agent user and minimal environment, with the login pseudo terminal wrapping sudo.
- Production startup requires an agent user. Container checks verify that it is bot and validate sudo denial messages.
- Workspace permissions are restored explicitly after creation and on reuse without default ACLs. Preparation errors are logged on the server and hidden from chat.
- Agent stderr is drained through a pipe with only its last 4 KB retained for failure diagnostics.
